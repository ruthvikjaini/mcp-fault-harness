# Adapting this harness to a real MCP server

The simulated servers in `src/mcp_fault_harness/servers.py` implement
the shape of MCP `tools/list` / `tools/call` in-process. The client
logic in `agents.py` (`ResilientClient`) does not depend on the
simulation: it depends on a `call(tool, arguments, now_ms,
idempotency_key)` function returning a payload or raising
`ToolError`. To point it at a real server, replace the server call
with a transport call and map the transport's failures onto the error
kinds in `protocol.py`. Nothing in this document has been tested
against a live server; it is a wiring guide, not a verified
integration.

## Transport sketch

```python
# Pseudocode only — not executed or tested in this repository.
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

class StdioTransport:
    def __init__(self, command, args):
        self.params = StdioServerParameters(command=command, args=args)

    async def call(self, tool, arguments, *, now_ms, idempotency_key=None):
        async with stdio_client(self.params) as (read, write):
            async with ClientSession(read, write) as session:
                await session.initialize()
                result = await session.call_tool(tool, arguments)
                return result.structuredContent or {}, result.isError
```

Use the official MCP Python SDK (`mcp` package) for the transport;
do not hand-roll JSON-RPC framing. Keep the injector between the
agent and the transport exactly as in the simulation: the injector's
schedule is the only part that changes, from seeded to
scenario-driven.

## Error mapping

| Real-world signal | `ToolError` kind | Retryable? |
|---|---|---|
| Timeout waiting for a response | `timeout` | Yes, with a deadline |
| Connection reset / transport closed | `transport_error` | Yes |
| HTTP 500 / 502 / 503 from a remote server | `server_error` | Yes, with backoff |
| HTTP 429 | `rate_limited` | Yes, honour `Retry-After` |
| HTTP 401 / 403, expired token | `auth_expired` | No — refresh credentials first |
| Response fails schema validation | `malformed` | Only if the fault is transient |
| Response timestamp older than the freshness window | stale payload | No — validate, then fall back |
| Response received, effect uncertain (timeout on a write) | `timeout_after_apply` | Only with an idempotency key |

The mapping matters most for writes: never retry a write after an
ambiguous timeout without an idempotency key the server honours.
This project's simulation shows retries without one duplicating the
effect in 34% of write runs under the stress profile. The key must be
generated by the caller, stored with the result, and sent on every
retry of the same logical operation — including retries after a
process restart, which means the key store must be durable in
production, not in-memory as it is here.

## Production checklist

1. Validate every payload against the tool's schema from
   `tools/list`, and check freshness on any timestamped field,
   before treating a result as evidence. A 200 response with a
   missing field is a failure, not an answer.
2. Give every tool its own circuit breaker. A shared breaker lets
   one dead server take down every tool; a per-tool breaker fails
   fast only for the tool that is actually broken.
3. Keep fallback data visibly stale: mark it, score it, or display
   it as cached, and never let it silently become the answer of
   record.
4. Log every faulted call with tool, mode, persistence, and the
   policy decision taken (retry / fallback / abstain). The
   `faulted_calls` record in this project is the shape to keep.
5. Run fault injection in staging with seedable schedules, on the
   same shape of profile used here (permanent-heavy stress plus
   transient and intermittent conditions). Never inject faults in
   production traffic.
6. Measure resilience ratio (faulted score / fault-free score) per
   capability tier and per stack, not just headline accuracy. If a
   larger model does not retain more of its score under faults, the
   budget belongs in handling, not in scale.
7. Decide the abstention policy explicitly: guessing keeps
   completion at 100% and fills answers with ungrounded ones (30%
   of sub-answers in this project's stress simulation for the naive
   policy). Abstaining lowers completion and keeps the answers that
   remain grounded. That is a product decision, not a default.

# mcp-fault-harness

A protocol-aware fault-injection harness for MCP-style tool-calling
agents, plus the resilience policies that survive it.

The idea, from Iannillo et al. (2026): benchmarks assume MCP tools
answer correctly and on time, so capability scores mask operational
brittleness. Under a permanent-heavy stress profile drawn from real
MCP incident patterns, task-completion scores fell 60% (8.08 to 3.23
out of 10), and a 120B backbone retained no larger share of its
fault-free score than a 20B one — framework-level error handling
mattered more than scale. This repository reproduces that evaluation
shape with simulated servers, agents, and faults: a drop-in injector
sits on the tool-call path, faults are seedable and persistent, and
four policies are compared on the same tasks, so the effect of
handling — validation, retries, fallbacks, circuit breakers,
idempotency — can be measured instead of asserted.

No LLM calls, no API keys, no GPU, no network. Every measurement
below comes from seeded simulations in this repository
(`results/experiment.json`, regenerated by
`scripts/run_experiment.py`).

## Why this is useful

Anyone shipping an agent that calls external tools hits the same
failures:

- A tool times out, returns 500, or rate-limits — and the agent
  retries a write that already happened, applying it twice.
- A tool returns a payload with a field missing, or a value from an
  hour ago — and the agent accepts it as evidence and builds the
  rest of the plan on it.
- A tool stays broken — and the agent keeps hammering it, paying
  for every attempt, instead of failing fast.
- A tool fails and the agent answers anyway, from memory, with a
  plausible number nobody verified.

`mcp-fault-harness` gives each of those a named, testable mechanism:
validate the payload or accept silent damage; retry only retryable
failures; fall back to a visibly stale cache; open a per-tool circuit
breaker; send an idempotency key on every write; abstain when no
verified evidence remains instead of guessing.

## Fault model

Two axes, following Iannillo et al.: failure *mode* x *persistence*.
A `FaultSchedule` is drawn per run from a seed, so the same seed and
call sequence always produce the same faults.

Modes:

| Family | Modes |
|---|---|
| Explicit failures (visible) | `timeout`, `transport_error`, `server_error`, `rate_limited`, `auth_expired`, `malformed` |
| Corrupt successes (silent) | `stale` (old timestamp, outdated value), `partial` (field missing), `empty` (no value), `slow` (late; can exceed the timeout) |
| Ambiguous | `timeout_after_apply` — the write happened, the response was lost |

Persistence: `transient` (one call, then clears), `intermittent`
(each call faults with a set probability), `permanent` (every call to
an affected tool faults). Four conditions are measured:
`fault_free`, `transient`, `intermittent`, and `stress` — the
permanent-heavy profile (60% permanent, 25% intermittent, 15%
transient; 55% of tools affected). The stress weights are this
project's assumption; the paper reports the profile is
permanent-heavy, not a mode-by-mode breakdown (see
`docs/RESEARCH.md`).

## Policies

| Policy | Validate | Retries | Fallback | Breaker | Idempotency | Abstain |
|---|---|---|---|---|---|---|
| `naive` | No | 0 | No | No | No | No (guesses) |
| `retry` | Yes | 2, retryable only | No | No | No | No (guesses) |
| `fallback` | Yes | 1 | Stale cache | No | No | No (guesses) |
| `resilient` | Yes | 2, retryable only | Stale cache | Per-tool | Yes | Yes |

Auth failures are never retried: retrying expired credentials with
the same credentials cannot succeed. Fallback values are always
marked stale and earn 0.6 credit, never full credit.

## Tasks

13 tasks in 5 shapes over simulated catalog, billing, and orders
servers: `live_lookup`, `short_compute`, `long_chain` (up to 4
sequential steps, each depending on the previous step's observed
value), `join` (independent lookups combined), and `write`
(side-effecting orders and credit updates, scored on exactly-once
effects). One task calls the same tool twice so a circuit breaker can
engage within a single run.

## Measured results

Full grid: 4 profiles x 4 policies x 2 capability levels x 13 tasks x
25 seeds = 10,400 runs. Scores are 0–10 per task; `grounded` counts
only answers backed by a live, validated tool result. Resilience
ratio is faulted score / fault-free score for the same policy and
capability. All figures below are from `results/measured.json`.

### Headline: scale does not buy resilience, handling does

Mean score under the stress profile (fault-free in brackets):

| Policy | Small | Large | Resilience ratio, small | Resilience ratio, large |
|---|---|---|---|---|
| naive | 5.61 (9.10) | 5.92 (9.63) | 0.616 | 0.615 |
| retry | 6.07 (9.10) | 6.40 (9.63) | 0.667 | 0.665 |
| fallback | 7.49 (9.10) | 7.90 (9.63) | 0.824 | 0.821 |
| resilient | 7.68 (9.10) | 8.12 (9.63) | 0.844 | 0.843 |

The larger capability scores higher everywhere — 9.63 vs 9.10
fault-free — but retains almost exactly the same fraction of its
score under stress as the smaller one (naive: 0.615 vs 0.616;
resilient: 0.843 vs 0.844). That is the paper's finding reproduced
in simulation: the resilience ratio is set by the policy, not by
capability. Retries alone recover little under a permanent-heavy
profile (0.665) because a permanently broken tool does not clear;
the fallback is the step that recovers most of the loss (0.821).

### Completion stays high while quality collapses

Under stress, the guessing policies complete 100% of tasks while
scoring 5.61–6.40, and 30.0% of the naive policy's sub-answers are
guesses, with a further 8.2% accepted from corrupt payloads. The
resilient policy completes 95.4% (large) — it abstains on 4.2% of
sub-answers rather than guessing — and scores 8.12, of which 6.55 is
grounded. The gap between its headline score and its grounded score
is the stale-fallback contribution: recovery, honestly labelled.

### Long chains suffer most; short tasks least

Mean score by task shape under stress, large capability:

| Shape | naive | resilient |
|---|---|---|
| long_chain | 4.28 | 7.94 |
| write | 5.80 | 7.00 |
| join | 6.18 | 8.20 |
| live_lookup | 6.40 | 8.36 |
| short_compute | 8.40 | 9.68 |

One bad result cascades through a chain because each step consumes
the previous step's observed value; a single-step task can only lose
itself.

### Retries without idempotency duplicate writes

Under stress, 34% of write runs under the `retry` and `fallback`
policies applied the effect twice (a retry after an ambiguous
timeout, with no idempotency key). The `resilient` policy, which
sends an idempotency key the server honours, duplicated 0% of write
runs in every condition, as did the naive policy — which never
retries. Under intermittent faults the duplicate rate for retry
policies is 14%. Retrying writes is safe only with idempotency.

### Cost of handling

Under stress (large capability), the naive policy averages 2.00
calls and 225 virtual ms per run; the resilient policy averages 3.27
calls and 401 virtual ms — retries and fallbacks cost calls, and
under a permanent-heavy profile many of them are spent on a tool
that will not recover. The circuit breaker short-circuits 0.022
calls per run on average in this grid; runs are short, so the
breaker rarely reaches its threshold within one run — its value is
across repeated calls to the same tool, covered by the unit tests
in `tests/test_agents.py`, not by the grid. See
`docs/ADAPTING_TO_REAL_MCP.md` for the production reading.

### Comparison with the paper

These are simulation numbers, not paper numbers, and the two must
not be conflated. The paper (real gpt-oss models, real MCP stacks)
reports a 60% score drop under its stress profile (8.08 to 3.23)
and no resilience advantage for the 120B model (p = 0.96). This
simulation reports a 38.5% drop for the naive policy (9.63 to 5.92)
and resilience ratios equal to three decimal places across
capability levels. The magnitudes differ — simulated faults and
simulated agents are milder than the real ones — but the structure
agrees: permanent-heavy faults collapse quality while completion
stays high, long chains suffer most, and handling, not scale,
determines how much score survives.

## Limitations

- Agents are simulated error rates, not language models; the grid
  measures policy mechanics, not reasoning quality.
- Fault-profile weights and the stale-value model (previous-cycle
  value, 15% higher) are assumptions, stated in `docs/RESEARCH.md`.
- Servers are in-process; no real MCP transport is exercised. The
  adapter guide is unwritten-code guidance, not a tested
  integration.
- The fallback cache is a static snapshot; in production, cache
  freshness and invalidation are the hard part, and are not
  modelled here.
- Breaker behaviour is exercised mainly at unit-test level; the
  grid's short runs rarely trigger it.
